# OMP 18.2.6 host compatibility

## Investigation baseline

The upstream source inspected was tag `v18.2.6`, commit
`78b753124d11f8dd3ae73e2524125890ff7c977e`.

- `PluginManager.#validateInstalledExtensions()` resolves every declared entry
  and calls `loadExtensions()` before accepting an install:
  [`manager.ts` lines 389-413](https://github.com/can1357/oh-my-pi/blob/78b753124d11f8dd3ae73e2524125890ff7c977e/packages/coding-agent/src/extensibility/plugins/manager.ts#L389-L413).
- `loadExtensions()` imports each extension through `loadLegacyPiModule()` and
  then binds its factory to a `ConcreteExtensionAPI`:
  [`loader.ts` lines 402-480](https://github.com/can1357/oh-my-pi/blob/78b753124d11f8dd3ae73e2524125890ff7c977e/packages/coding-agent/src/extensibility/extensions/loader.ts#L402-L480).
- The compatibility loader canonicalizes historical and canonical pi package
  imports onto `@oh-my-pi`, including canonical imports themselves, to retain
  one host module/registry instance:
  [`legacy-pi-compat.ts` lines 772-823](https://github.com/can1357/oh-my-pi/blob/78b753124d11f8dd3ae73e2524125890ff7c977e/packages/coding-agent/src/extensibility/plugins/legacy-pi-compat.ts#L772-L823).
- Its package-root overrides serve `pi-ai`, `pi-coding-agent`, and `pi-tui`

  [`legacy-pi-compat.ts` lines 989-1023](https://github.com/can1357/oh-my-pi/blob/78b753124d11f8dd3ae73e2524125890ff7c977e/packages/coding-agent/src/extensibility/plugins/legacy-pi-compat.ts#L989-L1023).

  [`legacy-pi-virtual-module.ts` lines 103-144](https://github.com/can1357/oh-my-pi/blob/78b753124d11f8dd3ae73e2524125890ff7c977e/packages/coding-agent/scripts/legacy-pi-virtual-module.ts#L103-L144).

  [`legacy-pi-compat.ts` lines 2590-2622](https://github.com/can1357/oh-my-pi/blob/78b753124d11f8dd3ae73e2524125890ff7c977e/packages/coding-agent/src/extensibility/plugins/legacy-pi-compat.ts#L2590-L2622).

  [`types.ts` lines 1177-1200](https://github.com/can1357/oh-my-pi/blob/78b753124d11f8dd3ae73e2524125890ff7c977e/packages/coding-agent/src/extensibility/extensions/types.ts#L1177-L1200).

The reported Git-install failure was reproduced with exact Bun OMP 18.2.6 in
an isolated XDG data/state/cache tree. Validation failed while resolving the
bridge's deep `pi-coding-agent/extensibility/legacy-pi-ai-shim` graph. A minimal
extension importing only canonical host roots (`pi-coding-agent`, `pi-ai`, and
`pi-agent-core/compaction`) passed install validation under both exact 18.2.6
distributions. This rules out a general OMP canonical-import loader defect.

## Compatibility boundary

The bridge now uses:

- `pi.typebox.Type` for tool schemas;
- `pi.pi.Text`, `pi.pi.keyHint`, and `pi.pi.buildSessionContext` for public
  coding-agent/TUI/session behavior;
- the canonical `@oh-my-pi/pi-ai` host compatibility root for the host-owned
  event stream and its deliberate historical `getModels()` catalogue alias;
- `@oh-my-pi/pi-agent-core/compaction` only for the low-level compaction
  takeover. `ctx.compact()` is not interchangeable because it has no way to
  inject the bridge's `completeImpl`.

Model discovery remains extension-initialization-time work because provider
registration is collected before a session context (and therefore
`ctx.models`) exists. Discovery is refreshed for every extension factory bind,
rather than frozen at module evaluation.

All OMP packages remain optional peers. Exact `18.2.6` versions are present
only in `devDependencies`, so installed plugins do not materialize a second
private OMP runtime.
